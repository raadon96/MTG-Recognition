# Benchmark dataset stays on Google Drive via DVC, in a dedicated dataset-only account

The benchmark dataset (~600 MB of full-resolution card photos and scans) is private and must be readable by CI. We keep it in DVC with a Google Drive remote, because it is free, needs no card or new vendor, and the data is already there. The folder moves into a **dedicated Google account that holds nothing but the dataset**, because DVC's Drive backend hardcodes the full `auth/drive` OAuth scope (`pydrive2/fs/spec.py`) and cannot be narrowed to one folder: any token DVC creates can reach the whole Drive of whoever signs in, so that Drive must contain only the dataset.

- **The maintainer** is the only one who pushes. They sign in through the project's OAuth Desktop client as the dataset account. The OAuth app is published to **Production, unverified**: Testing-mode refresh tokens expire every 7 days, while an unverified Production app only shows a warning screen and caps the project at 100 users for its lifetime. Only the dataset account ever uses it.
- **Everyone else pulls with a read-only key**, both CI and human contributors. One `dataset-reader` **service account** is shared on the folder as **Viewer**, and each consumer gets their own JSON key, so revoking one person means deleting one key. A leaked key can only read the dataset. Nobody shares the dataset account's password, and contributors never run OAuth, because their own DVC token would reach their whole Drive. A service account can read a folder shared from a personal My Drive but cannot write to one (it has no storage quota), so it couldn't push anyway. `gdrive_use_service_account` lives in each consumer's local config or CI environment, not in the committed `.dvc/config`, so the maintainer's pushes keep using OAuth. CI's key is the GitHub secret `GDRIVE_CREDENTIALS_DATA`. CI caches the pulled data with `actions/cache` keyed on the DVC pointer file, so it downloads only when the dataset changes, and pulls the whole dataset rather than a subset.
- The remote URL addresses the folder by ID (`gdrive://<folder-id>`), not by a `root/...` path.
- Images are stored **as captured, at full resolution**. Pre-resizing would only save egress on backends that charge for it, and the benchmark would then measure re-encoded images instead of what a phone or scanner produces.

## Considered Options

- **OAuth refresh token as the CI secret** (Testing or Production): rejected, because the token grants read/write/delete on the owner's entire Drive, so a leak from CI exposes everything.
- **Sharing the dataset account's password with contributors**: rejected. It hands every holder full control of the account (delete the data, lock out the maintainer), revoking one person means changing the password for everyone, and 2-step verification makes shared sign-ins impractical.
- **Sharing the folder with contributors' own Google accounts (OAuth)**: rejected. Even with Viewer access to the folder, each contributor's DVC token reaches their whole Drive.
- **Service account for local push too**: rejected, because service accounts can't create files in a personal My Drive (shared drives need Workspace), and an Editor key on disk is another long-lived secret.
- **Cloudflare R2**: the fallback. Its tokens can be scoped to one bucket and to read-only, and egress is free, but it likely needs a card and adds a vendor. Switch if Google tightens policy on unverified apps or service-account access, or if Drive's usage limits bite CI.
- **Backblaze B2 / Git LFS**: rejected over egress and bandwidth caps (B2's free egress is about 3 full pulls a month; LFS is disabled for the rest of the month once its 10 GiB is exceeded). **Hugging Face**: rejected because DVC has no Hugging Face remote.
